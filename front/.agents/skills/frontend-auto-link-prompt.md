# Prompt: เพิ่มส่วนคำแนะนำการเชื่อมโยงอะไหล่-รุ่นรถอัตโนมัติ (Frontend เท่านั้น)

## บริบท

โปรเจกต์: ระบบจัดการสต็อกอะไหล่มอเตอร์ไซค์ (Motorcycle Parts Stock Management System)
Stack ปัจจุบัน: **Quasar + Vue 3 (Composition API)**
สถานะ: มีเฉพาะ **frontend** เท่านั้น ยังไม่มี database และ backend จริง — ให้ทำงานกับ **mock data ในไฟล์เดียว** ไปก่อน โดยออกแบบโครงสร้างข้อมูลให้พร้อมสลับไปเรียก API จริงในอนาคตโดยแก้โค้ดน้อยที่สุด

## ปัญหาที่ต้องแก้

หน้าจอปัจจุบัน "ตารางเปรียบเทียบความเข้ากันได้อะไหล่" ต้องเชื่อมโยงอะไหล่กับรุ่นรถทีละคู่ด้วยมือ (เลือกอะไหล่ + เลือกรุ่นรถ + กดปุ่มเชื่อมโยง) ทำให้ต้องเชื่อมซ้ำหลายรอบสำหรับอะไหล่ที่ใช้ได้กับหลายรุ่น

ต้องการเพิ่ม **ส่วน "คำแนะนำการเชื่อมโยงอัตโนมัติ"** ที่แสดงรายการที่ระบบ "แนะนำ" มาให้ (เช่น จากการ match แพลตฟอร์ม/เครื่องยนต์ร่วม) แล้วให้แอดมินกดยืนยันทีเดียวหรือเลือกยืนยันเป็นชุด แทนการกดเชื่อมทีละคู่

## สิ่งที่มีอยู่แล้ว

มี component ต้นแบบชื่อ `AutoLinkSuggestions.vue` (แนบมาพร้อม prompt นี้) ที่ทำ mock data + UI ไว้ครบแล้ว ประกอบด้วย:
- รายการคำแนะนำ พร้อมชื่อ/รหัสอะไหล่, รุ่นรถที่แนะนำให้เชื่อม, รหัสแพลตฟอร์ม, เหตุผล, % ความเชื่อมั่น
- เลือกทั้งหมด / เลือกเฉพาะรายการ แล้วยืนยันเป็นชุด
- ยืนยัน/ปฏิเสธรายตัว
- จุดที่ต้องต่อ backend ทีหลังมาร์คไว้เป็นคอมเมนต์ `// TODO:` ในฟังก์ชัน `confirmOne`, `confirmSelected`, `dismissOne`

## งานที่ต้องทำ

1. **นำ `AutoLinkSuggestions.vue` ไปวางในโปรเจกต์จริง** ที่ path ที่เหมาะสมตามโครงสร้างโปรเจกต์ที่มีอยู่ (เช่น `src/components/parts/AutoLinkSuggestions.vue` หรือตามคอนเวนชันเดิมของโปรเจกต์)
2. **ปรับสไตล์ให้ตรงกับธีมของระบบเดิม** — ให้ตรวจสอบไฟล์ theme/variables (เช่น `quasar.variables.scss` หรือ config สี) ของโปรเจกต์จริง แล้วปรับสี/ระยะห่าง/ฟอนต์ให้ตรงกัน แทนการใช้สีที่ hardcode ไว้ใน mock component
3. **นำ component ไปวางในหน้า "ตารางเปรียบเทียบความเข้ากันได้อะไหล่"** (หน้าเดิมตามภาพตัวอย่างที่แนบ) โดยวางไว้เป็นส่วนเสริมเหนือหรือใต้ตาราง "เครื่องมือค้นหาและเชื่อมโยงอะไหล่" เดิม ไม่ใช่แทนที่ของเดิม (ของเดิมยังต้องใช้เชื่อมมือแบบ manual สำหรับเคสพิเศษ)
4. **เพิ่ม toggle/tab** ให้แอดมินสลับดูได้ระหว่าง "เชื่อมโยงด้วยมือ" (หน้าจอเดิม) กับ "คำแนะนำอัตโนมัติ" (component ใหม่) เช่น ใช้ `q-tabs` หรือ `q-expansion-item` แล้วแต่ความเหมาะสมกับ layout เดิม
5. **ขยาย mock data ให้ครอบคลุมเคสทดสอบเพิ่มเติม** เช่น:
   - อะไหล่ที่แนะนำแล้วแต่ user เคยปฏิเสธไปแล้ว (ไม่ควรขึ้นซ้ำ)
   - เคส confidence ต่ำที่ควรมี warning ชัดเจนกว่าเดิม
   - เคสไม่มีคำแนะนำเหลือ (empty state ที่มีอยู่แล้วใน component ต้นแบบ)
6. **เขียน mock service layer แยกออกมา** (เช่น `src/services/mockCompatibilityService.js`) ที่ export function `getSuggestions()`, `confirmSuggestion(id)`, `dismissSuggestion(id)` คืนค่าเป็น Promise (จำลอง async เหมือน API จริง) เพื่อให้ component เรียกผ่าน service layer แทนการผูก mock data ไว้ในตัว component ตรงๆ — จะได้สลับไปเรียก API จริงในอนาคตโดยแก้แค่ไฟล์ service ไฟล์เดียว ไม่ต้องแตะ component

## ข้อควรระวัง

- ห้ามใช้ `localStorage` เก็บสถานะ suggestion ที่ถูกปฏิเสธ/ยืนยันแล้ว ให้เก็บใน state ของ Vue (Pinia store หรือ props/emit ตามที่โปรเจกต์เดิมใช้อยู่) เพราะยังไม่มี backend จริงจะได้ไม่ยึดติดกับ pattern ที่ต้องเปลี่ยนทีหลัง
- ชื่อฟิลด์ใน mock data (`partId`, `modelId`, `platformCode`, `source`, `confidence`) ให้คงไว้ตามเดิม เพราะออกแบบให้ตรงกับ field ที่จะได้จาก backend จริงในอนาคต (ดูเอกสาร spec เดิม: การจับคู่ผ่านรหัส OEM/แพลตฟอร์มร่วม)
- คอมเมนต์ `// TODO:` ที่มีอยู่ในไฟล์ต้นแบบ ให้คงไว้และขยายเพิ่มถ้าจำเป็น เพื่อให้รู้ตำแหน่งที่ต้องแก้ตอนต่อ backend จริง

## Deliverables

- `AutoLinkSuggestions.vue` ที่ปรับสไตล์ให้ตรงกับธีมโปรเจกต์แล้ว วางในตำแหน่งที่ถูกต้อง
- `mockCompatibilityService.js` (หรือชื่อตามคอนเวนชันโปรเจกต์) แยก mock data/logic ออกจาก component
- ปรับหน้า "ตารางเปรียบเทียบความเข้ากันได้อะไหล่" ให้มี tab/toggle สลับดู manual vs auto-suggestion ได้
- Mock data ที่ครอบคลุมเคสทดสอบตามข้อ 5
